
# HWV-CM 人文关怀版 v2

**文件名：** PRODUCT_ARCHITECTURE_v2.md  
**版本：** 2.2.4  
**状态：** 架构修订版（A01–A05 全部修正完成），等待技术顾问最终放行复审  
**产品定位：** 帮助人理解自己、理解彼此、梳理关系事件并逐步改善相处方式的私密研究原型。

---

## 1. 产品改版目标

### 1.1 核心定位

本轮改版不是简单的视觉换肤，而是从产品认知、信息架构、交互方式和用户语言四个方面进行体验重构。

| 第一版 | 第二版 |
|---|---|
| 关系分析工具 | 理解自己与他人的陪伴空间 |
| 功能入口平铺 | 按自然认知顺序引导 |
| 数据与状态展示 | 叙述式体验 |
| 分析和测评感 | 理解与探索感 |
| 操作导向 | 用户感受导向 |

产品不得提供人格诊断、道德评分、关系匹配率或关系预测。

### 1.2 六个导航入口与五段认知动线

产品采用六个一级导航入口：

1. 首页
2. 认识自己
3. 理解彼此
4. 面对一件事
5. 一起改善
6. 回顾成长

首页承担全局入口和进度续接功能，其余五项构成认知体验主线。

五段认知动线：

- 认识自己：了解自己的感受、需求、习惯和相处方式。
- 理解彼此：探索不同视角，不预设双方必然一致。
- 面对一件事：从具体事件出发，区分事实、解释、感受和需求。
- 一起改善：在自愿、安全的前提下形成可执行的相处约定。
- 回顾成长：回看约定执行情况，记录变化，并自主决定是否更新个人档案。

并非所有用户都必须完成全部阶段。用户可以跳过非必要体验，但不能绕过安全检查、必要授权和关键数据确认。

## 4. 核心业务模块

### 4.1 个人档案

目标：帮助用户逐步了解自己的相处习惯。

设计要求：

1. 一次只呈现一个主要问题。
2. 支持跳过、保存和修改。
3. 支持随时退出。
4. 不把用户回答转化为人格裁定。
5. 不输出道德评分。
6. 默认保持私密。
7. v2 为单人本地模式，不存在向另一方共享的路径；共享授权机制为未来预留。
8. 档案回写必须经过用户主动确认。

### 4.2 关系差异地图

必须区分单人模式和双方模式。

**单人模式：**

- 只展示用户自己的观察。
- 展示用户认为可能存在的共同点。
- 展示用户感受到的差异。
- 展示尚未验证的问题。
- 不得将个人推测包装成双方共同结论。
- 不得声称已经了解另一方的真实想法。

**双方模式（v2 未开放，预留边界）：**

- v2 实际交付范围仅单人视角，双人实时共享保持「未开放」，与第一版一致（EventConsentPage 明示）。
- 未来开放双人模式必须满足：双方独立身份验证、独立授权记录、服务端可信存储与访问控制、撤回后多端失效同步（如 Cloudflare KV / Durable Objects 等协调机制）、退出数据处置；以上任一未实现则不得开放。
- 明示：已被对方看见或另行保存的内容无法通过撤回追回。

### 4.3 事件梳理

事件模块是产品核心业务流程。

业务步骤：

1. 开始前的知情说明与安全关怀。
2. 用户私密叙述。
3. 事实整理。
4. 不同解释。
5. 感受整理。
6. 需求整理。
7. 本人确认。
8. 可选方向。
9. 生成三份整理结果。

设计要求：

- 原始用户输入必须保留。
- 加工内容必须能够追溯到原始输入。
- 不得将系统推断当成事实。
- 用户可以返回修改自己的内容。
- 用户可以跳过非必要步骤。
- 不得强迫用户进入共同协商。
- 必须遵循 SAFETY 安全状态机及路由限制。

### 4.4 三份整理结果

三份整理结果不是测评结论，而是帮助用户重新理解事件的材料。

| 整理结果 | 内容 |
|---|---|
| 事实与经过 | 用户描述的事件、时间及可确认事实 |
| 不同理解 | 不同解释、待验证假设、感受与需求 |
| 可选方向 | 用户可以考虑的行动及需要进一步确认的问题 |

所有推断必须明确标记为「待验证假设」。

不得把解释当成事实，也不能替用户判断另一方的真实意图。

### 4.5 一起改善：共同约定

共同约定（v2 单人视角）：

1. 用户主动选择建立约定。
2. 约定记录用户本人意愿：想改善的具体事情、本人愿意尝试的行动、回顾时间。
3. 约定修改与结束由用户自主决定。
4. 双方明确同意、授权撤回、单方退出、双方各自行动项等双人能力，均为未来预留，v2 不承诺、不展示。

### 4.6 回顾成长

复盘内容：

1. 当初希望改善什么。
2. 实际发生了什么。
3. 哪些事情有所变化。
4. 哪些地方仍然困难。
5. 自己有哪些新的认识。
6. 是否愿意更新个人档案。

设计要求：

- 不将复盘结果作为关系评分。
- 不评价用户是否做得足够好。
- 支持修改和删除复盘内容。
- 档案回写必须经过用户主动确认。
- 不得将复盘内容自动共享给另一方。


## 5. 事件状态机

### 5.1 事件状态定义（严格对齐第一版源码 WorkflowStatus 八态）

| 状态 | 说明 | 后续 |
|---|---|---|
| CONSENT | 知情同意 | 安全检查 |
| SAFETY_CHECK | 安全检查 | 继续或安全出口 |
| PRIVATE_INTAKE | 私密叙述 | 事实整理 |
| FACT_MAP | 事实整理 | 不同理解 |
| HYPOTHESES | 不同理解（假设整理） | 本人确认 |
| INDIVIDUAL_CONFIRMATION | 本人确认 | 可选方向 |
| OPTIONS | 可选方向 | 生成三份整理结果 |
| SAFETY_SUPPORT | 安全支持出口 | 停留支持，不得推进共同协商 |

以上八态名称与 `eventMachine.ts`、`domain.ts` 的 WorkflowStatus 完全一致，仅作程序内部使用，不得直接展示给用户。

### 5.2 一版八态基线

事件核心流程按源码原始顺序流转：

CONSENT → SAFETY_CHECK → PRIVATE_INTAKE → FACT_MAP → HYPOTHESES → INDIVIDUAL_CONFIRMATION → OPTIONS

SAFETY_SUPPORT 为安全出口状态：不安全、不确定或拒绝回答时进入，绝不作为正常推进路径。本修订不新增、不删除、不合并任何既有状态。

### 5.3 FEELINGS_NEEDS 归属说明

FEELINGS_NEEDS 不是 WorkflowStatus，不是独立状态。它是一版源码中的用户输入数据字段归属，表示"感受与需求"数据，挂接在事件流程各阶段的数据结构中，参与内容整理与来源关联，不参与状态转换。不得将其虚构为状态机节点。

### 5.4 转换条件

| 从 | 到 | 转换条件 |
|---|---|---|
| CONSENT | SAFETY_CHECK | 用户完成知情同意并开始 |
| SAFETY_CHECK | PRIVATE_INTAKE | 安全状态为 clear 且用户选择继续 |
| SAFETY_CHECK | SAFETY_SUPPORT | 用户有担忧、不确定或不想回答 |
| SAFETY_SUPPORT | 仅停留 | 提供支持，不自动推进；不得进入共同协商流程 |
| PRIVATE_INTAKE | FACT_MAP | 用户提交私密叙述 |
| FACT_MAP | HYPOTHESES | 用户完成事实整理 |
| HYPOTHESES | INDIVIDUAL_CONFIRMATION | 用户完成不同理解整理 |
| INDIVIDUAL_CONFIRMATION | OPTIONS | 用户确认内容无误 |
| OPTIONS | 产出节点 | 生成三份整理结果 |

说明（与源码 transitions 完全一致）：状态机不允许任何前序跳转。确认页的「修改」通过把 hypothesis 的 choice 改为 `revised` 并填写 revision 内容实现（`areHypothesesConfirmed` 校验），内容可改但状态不跳回。

任意状态均允许用户退出、保存后离开；保存恢复必须经过统一状态转换入口，不允许绕过状态校验。

### 5.5 保存恢复与异常处理

1. 合法状态下随时保存。
2. 恢复时校验当前状态与目标页面是否匹配。
3. 状态不一致时提示用户选择继续或重新开始。
4. 异常中断应尽可能保留已持久化数据；恢复失败时保留快照及操作日志，提示用户人工处理，不承诺绝对零丢失。
5. 恢复后安全检查中用户有担忧，重新进入 SAFETY_SUPPORT。


## 6. 路由守卫、数据关联与删除

### 6.1 路由守卫

1. 未开始安全确认前，不得进入事件梳理流程。
2. 安全状态不是 clear 时，不得进入共同协商流程。
3. 用户有担忧、不确定或不想回答时，必须停留在 SAFETY_SUPPORT，不得跳过。
4. SAFETY_SUPPORT 不得返回共同协商流程。
5. 未完成本人确认前，不得生成三份整理结果。
6. 未获得双方明确授权前，不得展示双方比较内容（双方授权为未来预留能力，v2 双人模式未开放、不产生双方比较，此条不对应 v2 现行功能）。
7. 任意页面刷新、返回或恢复，均须重新校验路由许可。

### 6.2 数据关联规则

事件、整理结果、约定、复盘、档案之间的关联关系：

| 数据 | 关联内容 |
|---|---|
| 事件 | 叙述、事实、解释、感受与需求、整理结果 |
| 整理结果 | 对应事件的三份材料 |
| 约定 | 对应事件、本人意愿记录、回顾时间（双方同意记录为未来预留，v2 不产生） |
| 复盘 | 对应约定或事件、成长记录 |
| 档案 | 个人输入、回写来源 |

所有关联均记录来源标识，任何加工内容可追溯到原始输入。

### 6.3 删除策略

1. 删除事件时，级联删除其整理结果；已形成约定的，提示关联将解除。
2. 删除约定时，解除与事件、复盘的关联。
3. 删除复盘时，解除与事件、约定的关联，可选择是否保留成长记录。
4. 删除个人档案时，解除全部本地关联数据。
5. 清除事件记录必须经过用户明确确认。
6. 删除操作的确认、执行与结果提示均需完整记录。
7. 双方同意记录、共享授权解除、共享数据立即失效等双人共享能力为未来预留，v2 不承诺。

### 6.4 路由一致性方案（A03）

1. 统一校验入口：所有进入受保护路由的动作（导航、刷新、浏览器返回、直接输入 URL）统一调用 `guardRoute(path, event)`，返回值非 null 则重定向并提示。
2. 刷新恢复：读 localStorage 恢复 workspace → 用 guardRoute 校验当前路径 → 不匹配则跳转并提示「继续上次 / 重新开始」。
3. 浏览器返回：每次路由变化都重新执行 guardRoute，不重复信任历史记录。
4. 多标签页冲突：每个事件记录带单调递增 `revision` 字段，每次状态转换或内容修改时 +1；写入前比较本地 revision 与存储中的当前 revision，不一致说明其他标签页已修改，拒绝覆盖并提示用户查看差异后选择「以我的为准 / 保留对方版本 / 合并」；冲突解决后重新写入并递增 revision。**并发边界（如实说明）**：revision 比较后写入属于「尽力冲突检测」，不是严格并发控制——优先使用 Web Locks API 对同一事件的「读取 → 比较 → 写入」加锁，并用 storage 事件或 BroadcastChannel 通知其他标签页重新读取；不支持加锁的环境退化为「单标签页可写、其他标签页只读提示」，不承诺完全避免并发覆盖。revision 只在同一设备生效，不承载跨设备同步语义。
5. 异常恢复：transitionEvent 抛错时捕获并回退到最近合法状态，不覆盖已保存数据；恢复后不得直接依赖回退结果，须执行恢复态验证——校验恢复后的状态是否合法（在 transitions 允许范围内）、数据完整性是否达标（关键字段齐全、假设与确认状态一致）；验证失败则保留恢复现场并提示人工处理，不得继续业务流程。

### 6.5 数据生命周期方案（A05）

1. 迁移失败回滚：迁移前校验当前数据结构版本号并记录源/目标版本号，不匹配则不执行；迁移前写完整快照并用 **SHA-256 摘要**校验快照完整性；迁移失败（抛错、校验失败或写入失败）立即终止、回滚快照，保留旧版本数据，不写新结构；只有迁移数据验证成功后才更新版本号并清理快照；如果恢复本身失败，保留快照并提示人工恢复，不能静默清理；提供迁移失败恢复验证步骤（模拟损坏数据 + 模拟迁移中断，确认可恢复且旧数据不丢失）。
2. 级联删除事务性（localStorage 无多记录事务，采用「快照 + 操作日志 + 恢复」，如实描述为尽力恢复，不承诺绝对原子回滚、不承诺零丢失）：删除前将完整 workspace 写入临时快照键并校验快照完整写入成功；每个删除步骤按「先记录操作意图 → 执行删除 → 再记录完成状态」的日志顺序执行；任一步失败依据日志逆序恢复已删对象；恢复以快照为基准，但不得覆盖删除操作期间新写入的数据（新数据通过时间戳 + 与快照 diff 识别，先提示用户再决定合并或放弃）；恢复操作以日志步骤号为幂等键，已恢复步骤跳过，避免重复恢复造成重复或覆盖；恢复失败时保留快照与日志（恢复现场），允许下次启动继续恢复，不清理；全部步骤成功才确认删除完成并清理快照与日志。localStorage 容量不足或快照写入失败时，必须终止删除，不得继续执行。
3. 删除失败重试：提供明确重试入口，失败原因可见；启动时检查是否存在未完成的删除任务（有日志无完成标记），自动恢复并提示。
4. 数据损坏恢复：读取 localStorage 时校验结构完整性，损坏时提示并提供最近可用备份恢复。
5. 关联保留策略：删除父级时提示将解除的关联；已形成约定的删除需用户确认关联解除后再执行。
6. 隐私边界：localStorage 仅为本地原型存储，不声明为安全存储；生产方案另行评审。


## 7. 隐私承诺边界

1. 所有个人输入默认私密保存，不公开；v2 实际交付为单人本地私密数据（localStorage），不产生任何双方共享内容。
2. 双人授权、共享、撤回及多端失效均为未来预留能力，v2 未开放、不承诺（纯前端 localStorage 无法实现跨设备即时失效）。
3. 不收集与产品功能无关的个人信息。
4. 隐私说明与数据管理置于辅助入口，说明保存与删除方式及本地存储边界。
5. 删除个人档案前必须明确确认，并提供删除后果说明。
6. 产品内不提供、不编造任何热线号码；涉及安全支持时仅引导用户自行联系当地可信资源。
7. 分析、整理结果不用于任何评分、排名或第三方使用。

## 8.5 双人模式预留边界（v2 未开放）

**现状（v2 实际交付范围）：** 双人实时共享保持「未开放」，与第一版一致（第一版 EventConsentPage 已明示双人共享暂未开放）。v2 仅支持单人视角：展示用户自己的观察、认为可能存在的共同点、感受到的差异、尚未验证的问题；不展示任何双方比较结论，不承诺任何人已经了解另一方。

**预留开放条件（未来开放双人模式必须全部满足，任一未实现则不得开放）：**

1. 双方独立身份验证，输入内容按「我方 / 对方」隔离存储。
2. 独立授权记录：授权人、授权时间、授权范围、失效条件；共享展示前重新校验授权是否仍有效。
3. 服务端可信存储与访问控制（如 Cloudflare KV / Durable Objects 等协调机制），用于授权同步与多端失效。
4. 撤回后多端立即失效：撤回时删除或标记共享数据失效，展示层每次渲染前校验授权，缓存不保留已失效副本。
5. 单方退出后的数据处置：退出后对方不可再读取共享数据，已形成的约定按约定退出流程处理。

**明示边界：** 已被对方看见或另行保存的内容，无法通过撤回授权追回；隐私说明中必须明示。

## 9. 首页续接机制

1. 首页根据保存状态展示「接着上次」入口。
2. 续接记录包含：上次所在状态、事件标识、时间。
3. 点击续接时校验当前状态与目标页面匹配，不匹配则提示继续或重新开始。
4. 无续接记录时不做虚假提示。
5. 续接后安全检查有担忧时，重新进入 SAFETY_SUPPORT。

## 10. 空状态与路由异常

1. /event 无进行中事件时，展示空状态引导：开始一次梳理。
2. /report 无整理结果时，展示空状态引导：先完成一次事件梳理。
3. 空状态页面提供明确的返回入口，不展示空白页。
4. 无效或越权路由，统一跳转到首页并提示原因。
5. 任何异常路由不得绕过状态校验。

## 11. 设计与交互原则

1. 视觉方向：温暖、克制、留白，减少测评感。
2. 交互原则：一次一问、可跳过、随时保存、随时退出。
3. 文案替换表：页面文案用用户可理解语言（如「写下经过」「理清事实」），状态机名称仅内部使用。
4. 系统推断一律标记「待验证假设」。
5. 不得使用诊断、评分类表述。

## 12. 技术架构约束

1. 前端：React + TypeScript，与现有代码库保持一致。
2. 数据存储：localStorage 为主，迁移版本号管理。
3. 所有状态转换经过统一转换入口，保证幂等。
4. 数据结构升级时提供迁移，不丢失用户数据。
5. 生产构建与线上版本分离，未经批准不覆盖 Cloudflare 线上版本。
